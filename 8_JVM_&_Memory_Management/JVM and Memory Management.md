# JVM and Memory Management

# JVM

### 1. What is JVM?

**JVM (Java Virtual Machine)** is the runtime environment that executes Java **bytecode**.

The Java compiler (`javac`) converts `.java` source code into `.class` bytecode, and the JVM loads and executes that bytecode.

Flow:

```
Java Source Code
      ↓
    javac
      ↓
  Bytecode (.class)
      ↓
     JVM
      ↓
   Machine Code
      ↓
     CPU
```

The JVM is responsible for:

- Loading classes
- Verifying bytecode
- Managing memory
- Executing bytecode
- Garbage collection
- Providing platform independence

Important interview point:

> Java is platform-independent because bytecode is platform-independent, while the JVM implementation is platform-specific.
> 

For example:

```
Same .class file
       ↓
  ┌─────┼─────┐
  ↓     ↓     ↓
 JVM   JVM   JVM
Windows Linux macOS
```

The same bytecode can run on different operating systems as long as an appropriate JVM exists.

---

### 2. JVM Architecture

JVM architecture can be divided into major components:

```
                    JVM
                     |
         ┌────────────┼────────────┐
         ↓            ↓            ↓
   Class Loader   Runtime Data   Execution
                    Areas         Engine
         |             |             |
         |             |        ┌────┼────┐
         |             |        ↓    ↓    ↓
         |             |    Interpreter
         |             |    JIT Compiler
         |             |    GC
         |
         ↓
      Bytecode
         |
         ↓
    Native Method Interface
         |
         ↓
    Native Libraries
```

The major components are:

1. **Class Loader**
2. **Runtime Data Areas**
3. **Execution Engine**
4. **JNI (Java Native Interface)**
5. **Native Libraries**

---

### 3. What is Bytecode?

**Bytecode** is the intermediate instruction set generated by the Java compiler.

Example:

```java
public class Demo {
    public static void main(String[] args) {
        System.out.println("Hello");
    }
}
```

Compilation:

```bash
javac Demo.java
```

This generates:

```
Demo.class
```

The `.class` file contains **bytecode**, which the JVM executes.

Important:

```
.java
  ↓ javac
.class (bytecode)
  ↓ JVM
Machine code
```

Bytecode is **not directly machine code**.

This is one of the main reasons Java achieves portability.

---

### 4. What is a Class Loader?

The **Class Loader** is a JVM component responsible for loading `.class` files into memory when classes are required.

For example:

```java
Student s = new Student();
```

When `Student` is required, the Class Loader loads the `Student.class` bytecode.

The Class Loader performs three major stages:

```
Loading
   ↓
Linking
   ↓
Initialization
```

Linking itself contains:

```
Verification
   ↓
Preparation
   ↓
Resolution
```

So:

```
Class Loader
    |
    ├── Loading
    |
    ├── Linking
    |     ├── Verification
    |     ├── Preparation
    |     └── Resolution
    |
    └── Initialization
```

Interview point:

> Class loading is generally lazy: a class is loaded when it is needed, although JVM behavior can involve earlier loading for some situations.
> 

---

### 5. Types of Class Loaders

The JVM has a class-loader hierarchy.

Important built-in loaders are:

```
Bootstrap ClassLoader
        ↓
Platform ClassLoader
        ↓
Application ClassLoader
```

**Bootstrap ClassLoader**

- Loads core Java classes.
- Examples: classes from `java.lang`, `java.util`, etc.
- Implemented as part of the JVM/native runtime.

**Platform ClassLoader**

- Loads platform classes/modules.

**Application ClassLoader**

- Loads classes from the application classpath/module path.
- This is typically the loader responsible for your application classes.

Example:

```java
public class Demo {
    public static void main(String[] args) {
        System.out.println(Demo.class.getClassLoader());
    }
}
```

For an application class, this typically prints the application class loader.

Important interview question:

> Why is `String.class.getClassLoader()` `null`?
> 

Because `String` is loaded by the **Bootstrap ClassLoader**, and the bootstrap loader is represented as `null` in the Java API.

---

### 6. What is Runtime Data Area?

**Runtime Data Areas** are memory areas created/used by the JVM while executing a Java program.

The major areas are:

```
Runtime Data Areas
       |
       ├── Heap
       ├── Method Area
       ├── JVM Stack
       ├── PC Register
       └── Native Method Stack
```

Some areas are **shared among threads**, while others are **per-thread**.

```
Shared:
    Heap
    Method Area

Per Thread:
    JVM Stack
    PC Register
    Native Method Stack
```

This distinction is very important for interviews.

---

### 7. What is the Execution Engine?

The **Execution Engine** executes the bytecode loaded into the JVM.

Its major components are:

```
Execution Engine
      |
      ├── Interpreter
      ├── JIT Compiler
      └── Garbage Collector
```

**Interpreter**

- Executes bytecode instruction by instruction.
- Starts execution quickly.
- Can be slower for frequently executed code.

**JIT Compiler**

- Identifies frequently executed code.
- Compiles it into native machine code.
- Improves performance during long-running execution.

**Garbage Collector**

- Automatically identifies and removes objects that are no longer reachable.

---

### 8. What is JIT Compiler?

**JIT (Just-In-Time) Compiler** converts frequently executed bytecode into **native machine code at runtime**.

Without JIT:

```
Bytecode
   ↓
Interpreter
   ↓
Execute instruction by instruction
```

With JIT:

```
Bytecode
   ↓
Frequently executed code
   ↓
JIT Compiler
   ↓
Native Machine Code
   ↓
CPU
```

For example:

```java
for (int i = 0; i < 1_000_000; i++) {
    calculate(i);
}
```

If `calculate()` becomes a frequently executed method, the JVM can optimize and compile it into native code.

This frequently executed code is often called a **hotspot**, which is why the JVM is commonly described as using hotspot-based compilation.

Important interview point:

> JIT compilation happens at runtime and is one of the major reasons Java applications can achieve high performance.
> 

---

### 9. Interpreter vs JIT Compiler

| Interpreter | JIT Compiler |
| --- | --- |
| Executes bytecode instruction by instruction | Compiles frequently executed bytecode to native code |
| Faster startup | Compilation has runtime overhead |
| Generally slower for hot code | Faster for repeatedly executed code |
| No need to compile large portions upfront | Optimizes hot code |
| Good for initial execution | Good for long-running applications |

Modern JVMs use a **combination of interpretation and JIT compilation**.

---

### 10. What is JNI?

**JNI (Java Native Interface)** is an interface that allows Java code to interact with **native code** written in languages such as C or C++.

Flow:

```
Java Code
    ↓
   JNI
    ↓
Native Code
(C/C++)
    ↓
Native Libraries / OS
```

Example use cases:

- Operating-system-specific functionality
- Existing native libraries
- Performance-critical native components
- Hardware/system-level integration

Example:

```java
public class NativeDemo {

    public native void execute();

    static {
        System.loadLibrary("nativeLib");
    }
}
```

`native` means the method implementation exists outside Java.

Important:

> JNI allows Java to call native code, but using native code reduces some of Java's platform independence and introduces additional complexity.
> 

---

# Memory Management

### 11. What is Heap Memory?

The **Heap** is the JVM memory area where **objects and arrays are allocated**.

Example:

```java
Student s = new Student();
```

Here:

```
Stack                  Heap
------                 ------
s  ─────────────────→ Student object
```

The reference variable `s` is stored in the stack frame, while the actual `Student` object is allocated on the heap.

Heap characteristics:

- Shared among threads
- Stores objects and arrays
- Managed by Garbage Collector
- Can be divided into different GC generations/regions depending on the garbage collector

Example:

```java
int[] arr = new int[100];
```

The array object is allocated on the heap.

Important interview point:

> Heap is shared between threads, so shared mutable objects can create concurrency problems.
> 

---

### 12. What is Stack Memory?

Each thread has its own **JVM Stack**.

Whenever a method is called, a **stack frame** is created.

Example:

```java
public static void main(String[] args) {
    calculate();
}

static void calculate() {
    int x = 10;
}
```

Conceptually:

```
Thread Stack

┌─────────────────┐
│ calculate()     │
│ x = 10          │
├─────────────────┤
│ main()          │
│ args            │
└─────────────────┘
```

When `calculate()` finishes, its stack frame is removed.

Stack generally contains:

- Local variables
- Method parameters
- Operand stack
- References to heap objects
- Return-related information

Important:

> Every thread has its own JVM stack, so stack memory is not directly shared between threads.
> 

---

### 13. Heap vs Stack

This is a very common interview question.

| Heap | Stack |
| --- | --- |
| Shared among threads | Private to each thread |
| Stores objects/arrays | Stores method frames and local execution data |
| Managed by GC | Frames removed automatically as methods return |
| Larger memory area generally | Usually smaller per-thread area |
| Can have GC-related overhead | Very fast allocation/deallocation of frames |
| `new Student()` object lives here | Reference/local variable may live in frame here |

Example:

```java
Student s = new Student();
```

Conceptually:

```
Stack                     Heap
------                    ------
s ─────────────────────→ Student object
```

One important nuance: JVM/JIT optimizations can change the physical placement of data. For interview purposes, use the conceptual model above.

---

### 14. What is the Method Area?

The **Method Area** is a JVM runtime data area that stores **class-level information**.

It contains information such as:

- Class metadata
- Method information
- Field information
- Runtime constant pool
- Information needed for method execution

It is **shared among threads**.

Conceptually:

```
Method Area
   |
   ├── Class Metadata
   ├── Method Metadata
   ├── Field Metadata
   └── Runtime Constant Pool
```

Important:

> Method Area is a JVM specification concept. The exact implementation is JVM-dependent.
> 

This becomes important when discussing **Metaspace**.

---

### 15. What is Metaspace?

**Metaspace** is the HotSpot JVM's implementation for storing class metadata, replacing the old **PermGen** approach starting in Java 8.

Before Java 8:

```
Method Area
     ↓
PermGen
```

Java 8+ HotSpot:

```
Method Area
     ↓
Metaspace
```

Metaspace is allocated from **native memory**, rather than being part of the traditional Java heap.

Important distinction:

```
Method Area
    = JVM specification concept

Metaspace
    = HotSpot JVM implementation detail
```

Interview question:

**What replaced PermGen?**

Answer:

> Metaspace replaced PermGen in Java 8.
> 

---

### 16. What is the PC Register?

**PC Register (Program Counter Register)** stores information about the **current/next bytecode instruction being executed by a thread**.

Each thread has its own PC register.

```
Thread 1 → PC Register
Thread 2 → PC Register
Thread 3 → PC Register
```

Why is it needed?

When a thread switches execution, the JVM needs to know where that thread should continue.

Important:

> PC Register is thread-private.
> 

For a Java method, it tracks the relevant bytecode execution position. For a native method, its value is not defined by the JVM specification.

---

### 17. What is Native Method Stack?

The **Native Method Stack** supports execution of **native methods**.

Native method:

```java
public native void execute();
```

When such a method executes:

```
Java Thread
    ↓
Java Method
    ↓
Native Method
    ↓
Native Method Stack
```

It is generally used when Java interacts with native code through mechanisms such as JNI.

Important:

> Like the JVM Stack, the Native Method Stack is associated with individual threads.
> 

The exact implementation is JVM-dependent, and some JVM implementations may combine or omit a separate native-method stack.

---

### 18. JVM Memory Areas — Final Interview View

You should be able to draw this from memory:

```
                         JVM
                          |
              ┌───────────┴────────────┐
              |                        |
        Runtime Data Areas        Execution Engine
             |
      ┌───────┼────────┬──────────┐
      ↓       ↓        ↓          ↓
    Heap   Method    JVM Stack   PC Register
           Area          |
                         |
                   Native Method Stack
```

Thread sharing:

```
              JVM
               |
        ┌──────┴────────┐
        ↓               ↓
     Shared          Per Thread
        |               |
      Heap          JVM Stack
      Method Area   PC Register
                    Native Method Stack
```

The most important interview relationships are:

```
.class
  ↓
Class Loader
  ↓
Runtime Data Areas
  ↓
Execution Engine
  ├── Interpreter
  ├── JIT
  └── GC
  ↓
Machine Code
```

And remember these four distinctions:

1. **Heap** → objects and arrays
2. **Stack** → per-thread method execution frames
3. **Method Area** → class-level metadata
4. **Metaspace** → HotSpot's native-memory implementation for class metadata

# Garbage Collection

### 19. What is Garbage Collection (GC)?

**Garbage Collection (GC)** is the JVM's automatic mechanism for identifying and reclaiming heap memory occupied by objects that are **no longer reachable** by the application.

Example:

```java
Student s = new Student();
s = null;
```

Initially:

```
s ───────→ Student Object
```

After:

```java
s = null;
```

```
s ───────→ null

Student Object
      ↑
   unreachable
```

The `Student` object becomes **eligible for garbage collection**.

Important:

> GC does not guarantee that an object will be collected immediately. It only means the object is eligible for collection.
> 

---

### 20. Why is Garbage Collection Needed?

Without automatic garbage collection, developers would have to manually release memory.

GC helps to:

- Automatically reclaim unused heap memory
- Reduce manual memory-management errors
- Prevent many types of memory leaks caused by forgotten deallocation
- Make Java development simpler and safer
- Reuse memory occupied by unreachable objects

Example:

```java
for (int i = 0; i < 1000000; i++) {
    Student s = new Student();
}
```

Many `Student` objects become unreachable after each iteration.

The JVM can eventually reclaim that memory.

Important:

> GC manages memory, but it does not eliminate all possible memory leaks. Objects that are still reachable but no longer logically needed can remain in memory.
> 

---

### 21. What is Mark and Sweep?

**Mark and Sweep** is a fundamental garbage-collection algorithm.

It works in two main phases:

```
Mark
  ↓
Sweep
```

#### Mark

The GC identifies objects that are still **reachable** from GC roots and marks them as alive.

```
Root
 ↓
Object A
 ↓
Object B

Object C   ← unreachable
Object D   ← unreachable
```

A and B are marked as live.

#### Sweep

The GC reclaims memory occupied by unmarked objects.

```
Before:

[A][B][C][D]
 ↑   ↑
live live

After Sweep:

[A][B][free][free]
```

Important:

> Mark identifies reachable objects; Sweep reclaims memory belonging to unreachable objects.
> 

A major drawback of a simple mark-and-sweep approach is **fragmentation**, because free memory can become scattered across the heap.

---

### 22. What is Generational Garbage Collection?

**Generational GC** is based on the observation that:

> Most objects die young.
> 

Instead of treating the entire heap equally, objects are divided into generations based on their age.

Conceptually:

```
Heap
 |
 ├── Young Generation
 |      |
 |      ├── Eden
 |      ├── Survivor 0
 |      └── Survivor 1
 |
 └── Old Generation
```

New objects generally start in the **Young Generation**.

Objects that survive multiple collections can eventually be promoted to the **Old Generation**.

This allows the JVM to collect short-lived objects more frequently and efficiently.

---

### 23. What is Young Generation?

The **Young Generation** is the area where newly allocated objects generally begin their lifetime.

Conceptually:

```
Young Generation
       |
  ┌────┼──────────┐
  ↓    ↓          ↓
Eden  Survivor 0  Survivor 1
```

New objects are typically allocated in **Eden**.

When a young collection occurs:

```
Eden
  ↓
Young GC
  ↓
Dead objects removed
  ↓
Surviving objects copied/promoted
  ↓
Survivor
  ↓
Survivor
  ↓
Old Generation
```

Objects that survive enough collections may be promoted to the Old Generation.

Important:

> The exact generation layout and behavior depends on the garbage collector. For example, G1 uses regions rather than the classic contiguous Young/Old layout.
> 

---

### 24. What is Old Generation?

The **Old Generation** contains objects that have survived enough GC cycles to be considered relatively long-lived.

Example:

```java
static List<Student> students = new ArrayList<>();
```

If objects remain reachable for a long time, they may eventually become candidates for the old/long-lived part of the heap.

Conceptually:

```
Young Generation
      ↓
Objects survive GC
      ↓
Old Generation
```

Old-generation collection is generally more expensive than collecting short-lived young objects because it can involve a larger portion of the heap.

---

### 25. What is Minor GC?

**Minor GC** traditionally refers to garbage collection focused on the **Young Generation**.

Typical process:

```
Eden
 ↓
Young GC
 ↓
Dead objects removed
 ↓
Surviving objects copied/promoted
```

Because most objects are short-lived, young collections can reclaim significant memory relatively efficiently.

Important interview point:

> "Minor GC" is a generational-GC term. Modern collectors such as G1 use terminology based on collection types and regions, so you should not assume every modern collector maps perfectly onto the classic Minor/Major terminology.
> 

---

### 26. What is Major GC?

Traditionally, **Major GC** refers to collection of the **Old Generation**.

Conceptually:

```
Old Generation
      ↓
Major GC
      ↓
Reclaim unreachable objects
```

It is generally more expensive than a young-generation collection because old-generation objects tend to live longer and there may be more memory to process.

Important:

> The exact meaning of "Major GC" is not completely standardized across JVM garbage collectors. In interviews, describe it as a traditional term for old-generation collection rather than treating it as a universal JVM event.
> 

---

### 27. What is Full GC?

**Full GC** generally means a GC operation that involves **the entire Java heap**, typically including both young and old regions/generations, and may also involve class metadata-related processing depending on the collector and JVM.

Conceptually:

```
Heap
 |
 ├── Young
 └── Old
      ↓
   Full GC
```

Full GC is usually expensive because a large amount of heap may need to be examined and reclaimed.

It can cause significant application pauses depending on the collector and circumstances.

Common reasons a Full GC may occur include:

- Allocation pressure
- Insufficient available heap
- Certain promotion failures
- Explicit `System.gc()` requests
- Collector-specific conditions

Important:

> `System.gc()` is only a request/hint to the JVM; it does not guarantee that a Full GC will occur.
> 

---

### 28. What is Stop-the-World (STW)?

**Stop-the-world** means that application threads are temporarily paused while the JVM performs a GC operation or another operation requiring exclusive JVM activity.

Example:

```
Application Threads
       ↓
RUNNING RUNNING RUNNING
       ↓
      PAUSE
       ↓
       GC
       ↓
     RESUME
```

During the pause:

```
Application threads → stopped
GC                  → working
```

Important:

> Stop-the-world is a property of a particular GC phase, not a separate garbage collector.
> 

Modern collectors such as G1 are designed to keep STW pauses relatively controlled, but they still have stop-the-world phases.

---

### 29. What is G1 Garbage Collector?

**G1 (Garbage-First) GC** is a modern, low-pause garbage collector designed for large heaps and predictable pause-time goals.

Instead of dividing the heap into one large contiguous Young and Old area, G1 divides the heap into many **equal-sized regions**.

Conceptually:

```
G1 Heap
┌────┬────┬────┬────┬────┐
│ R1 │ R2 │ R3 │ R4 │ R5 │
├────┼────┼────┼────┼────┤
│ R6 │ R7 │ R8 │ R9 │ R10│
└────┴────┴────┴────┴────┘
```

Each region can be classified as:

- Eden
- Survivor
- Old
- Humongous

The classification can change over time.

---

### 30. How does G1 GC work?

G1 tries to identify regions containing the most reclaimable garbage.

That's where the name comes from:

> **Garbage-First** → prioritize regions with more garbage.
> 

Simplified flow:

```
Heap divided into regions
          ↓
Identify regions with garbage
          ↓
Select collection set
          ↓
Mark/copy live objects
          ↓
Reclaim regions
```

G1 uses **copying/evacuation** to move live objects from selected regions into other regions.

This helps reduce fragmentation.

---

### 31. Important G1 GC Features

For interviews, remember these:

**1. Region-based**

Heap is divided into many regions instead of relying only on large contiguous generations.

**2. Garbage-first approach**

Regions with more reclaimable garbage are prioritized.

**3. Pause-time goal**

You can provide a target pause time using:

```
-XX:MaxGCPauseMillis=200
```

This is a **goal**, not a strict guarantee.

**4. Concurrent marking**

G1 performs important marking work concurrently with application execution.

**5. Evacuation**

Live objects are copied from selected regions to other regions.

**6. Humongous objects**

Very large objects can occupy one or more special **humongous regions**.

---

### 32. G1 GC vs Traditional Generational GC

| Traditional Generational Model | G1 |
| --- | --- |
| Young + Old areas | Heap divided into regions |
| Often described with Eden/Survivor/Old | Regions dynamically classified |
| Collection terminology commonly Minor/Major | Uses G1-specific collection phases |
| Can suffer from fragmentation depending on collector | Evacuation helps manage fragmentation |
| Less flexible region selection | Selects collection regions based on garbage |
| Older collectors commonly used this model | Designed for large heaps and predictable pauses |

One correction worth remembering:

> G1 is still **generational** in modern JDKs; it uses regions while logically maintaining young and old generations.
> 

---

### 33. Garbage Collection — Complete Interview Flow

You should be able to explain the complete process like this:

```
        new Object()
             ↓
        Young Generation
             ↓
          Young GC
         ↙         ↘
Dead objects    Surviving objects
     ↓                 ↓
 Reclaimed       Survivor regions
                       ↓
                 Multiple survivals
                       ↓
                  Old Generation
                       ↓
                 Old/Full collection
                       ↓
                 Unreachable objects
                       ↓
                    Reclaimed
```

And for G1:

```
               Java Heap
                   ↓
           Divided into regions
                   ↓
          Identify garbage-heavy
                 regions
                   ↓
             Collection Set
                   ↓
           Mark + Evacuate/Copy
                   ↓
          Reclaim selected regions
```

The **most important interview distinctions** from this section are:

- **GC** → automatic reclamation of unreachable heap objects.
- **Mark & Sweep** → mark reachable objects, sweep/reclaim unreachable ones.
- **Generational GC** → exploit the fact that most objects die young.
- **Young Generation** → newly allocated/short-lived objects.
- **Old Generation** → long-lived objects.
- **Minor GC** → traditionally Young Generation collection.
- **Major GC** → traditionally Old Generation collection.
- **Full GC** → broadly involves the entire Java heap.
- **STW** → application threads are paused during certain JVM/GC phases.
- **G1** → region-based, garbage-first, pause-time-oriented collector.

# Important JVM Memory Concepts

### 34. Stack vs Heap

This is one of the most frequently asked JVM interview questions.

| Stack | Heap |
| --- | --- |
| Per-thread memory | Shared among threads |
| Stores stack frames | Stores objects and arrays |
| Contains local variables, parameters, operand stack, etc. | Contains dynamically allocated objects |
| Method call creates a stack frame | `new` generally allocates an object on heap |
| Automatically released when method returns | Reclaimed by Garbage Collector |
| Limited per-thread size | Usually much larger |
| Excessive recursion can cause `StackOverflowError` | Excessive allocation can cause `OutOfMemoryError` |

Example:

```java
class Student {
    String name;
}

public class Demo {
    public static void main(String[] args) {
        Student s = new Student();
        s.name = "Atharva";
    }
}
```

Conceptually:

```
Thread Stack                 Heap
────────────                 ─────────────
s ────────────────────────→  Student Object
                             name → "Atharva"
```

Here:

- `s` is a reference stored in the `main()` stack frame conceptually.
- The `Student` object is allocated on the heap.
- The `"Atharva"` String is an object and is managed in heap-related memory according to JVM implementation.

Important nuance:

> The JVM specification does not require every reference/local variable to physically reside in the stack. JIT optimizations such as escape analysis can change physical allocation. The stack/heap model is the correct conceptual model for interviews.
> 

---

### 35. What is StackOverflowError?

`StackOverflowError` occurs when a thread's **JVM stack cannot accommodate additional stack frames**.

The most common cause is **infinite or excessively deep recursion**.

Example:

```java
public class Demo {

    static void test() {
        test();
    }

    public static void main(String[] args) {
        test();
    }
}
```

Execution:

```
main()
  ↓
test()
  ↓
test()
  ↓
test()
  ↓
...
  ↓
Stack memory exhausted
  ↓
StackOverflowError
```

Each method call creates another stack frame.

Eventually the thread's stack limit is exceeded.

Typical output:

```
java.lang.StackOverflowError
```

Important points:

- It is an **Error**, not an Exception.
- It is related to **thread stack exhaustion**.
- Infinite recursion is the classic cause.
- Increasing stack size can sometimes delay the problem, but it does not fix incorrect recursion.

Example JVM option:

```
-Xss2m
```

This sets a thread stack size target of approximately 2 MB, subject to JVM/platform behavior.

---

### 36. What is OutOfMemoryError?

`OutOfMemoryError` occurs when the JVM or a relevant runtime area cannot satisfy a memory allocation request.

A common case is **Java heap exhaustion**.

Example:

```java
import java.util.*;

public class Demo {
    public static void main(String[] args) {

        List<int[]> list = new ArrayList<>();

        while (true) {
            list.add(new int[1_000_000]);
        }
    }
}
```

The program continuously creates arrays and keeps references to them.

Eventually:

```
Heap
 ↓
Memory keeps increasing
 ↓
Heap cannot satisfy allocation
 ↓
OutOfMemoryError
```

Typical message:

```
java.lang.OutOfMemoryError: Java heap space
```

Other possible messages include:

```
OutOfMemoryError: Metaspace
```

or

```
OutOfMemoryError: unable to create native thread
```

So `OutOfMemoryError` is broader than simply "heap is full."

---

### 37. StackOverflowError vs OutOfMemoryError

Very common interview comparison:

| StackOverflowError | OutOfMemoryError |
| --- | --- |
| Stack memory exhausted | Memory allocation cannot be satisfied |
| Usually caused by deep/infinite recursion | Often caused by excessive allocation/retention |
| Related to thread stack | Commonly related to heap, but can involve other memory areas/resources |
| Example: infinite recursion | Example: continuously storing objects |
| `StackOverflowError` | `OutOfMemoryError` |
| Both extend `Error` | Both extend `Error` |

Hierarchy:

```
Throwable
   ↓
 Error
   ├── StackOverflowError
   └── OutOfMemoryError
```

### 38. What is a Memory Leak in Java?

A **memory leak** occurs when objects are no longer logically needed by the application but remain **strongly reachable**, preventing the Garbage Collector from reclaiming them.

Java has automatic GC, but it can still have memory leaks.

Example:

```java
import java.util.*;

public class Demo {

    static List<byte[]> cache = new ArrayList<>();

    public static void main(String[] args) {

        while (true) {
            cache.add(new byte[1024 * 1024]);
        }
    }
}
```

The objects inside `cache` may no longer be useful, but:

```
static cache
     ↓
   List
     ↓
Object
Object
Object
...
```

Because the objects are still reachable through `cache`, GC cannot reclaim them.

Eventually:

```
Memory usage ↑
      ↓
Heap fills
      ↓
OutOfMemoryError
```

Common causes of memory leaks:

- Static collections retaining objects
- Objects stored in caches without eviction
- Listeners/callbacks not deregistered
- Unbounded collections
- Incorrectly managed `ThreadLocal`
- Long-lived objects holding references to short-lived objects

Important:

> A Java memory leak is usually not "memory was never freed manually." It is typically **unwanted object retention caused by reachable references**.
>

### 39. Strong Reference

A **strong reference** is the normal type of Java reference.

Example:

```java
Student s = new Student();
```

Here:

```
s ─────→ Student Object
```

As long as the object is strongly reachable through live references, the GC generally **will not reclaim it**.

Example:

```java
Student s = new Student();
s = null;
```

Now, assuming no other references exist:

```
s → null

Student Object
      ↑
   unreachable
```

The object becomes eligible for GC.

Most Java references you write are **strong references**.

---

### 40. Weak Reference

A **weak reference** allows an object to be referenced without preventing the Garbage Collector from reclaiming that object.

Java provides:

```
java.lang.ref.WeakReference
```

Example:

```java
Student student = new Student();

WeakReference<Student> weak =
        new WeakReference<>(student);
```

Conceptually:

```
Strong reference:

student ─────→ Object
               ↑
             GC keeps it

Weak reference:

weak ─ - - - → Object
               ↑
           GC may reclaim it
```

If there are no strong references to the object, the GC may reclaim it.

After collection:

```java
weak.get()
```

may return:

```
null
```

Important:

> Weak references are useful when you want references that should not keep objects alive, such as certain caches or metadata structures.
> 

---

### 41. Strong vs Weak Reference

| Strong Reference | Weak Reference |
| --- | --- |
| Normal Java reference | `WeakReference<T>` |
| Prevents GC while strongly reachable | Does not prevent GC |
| `Student s = new Student()` | `new WeakReference<>(student)` |
| Object remains reachable | Object may be reclaimed |
| Most commonly used | Used for specialized memory-sensitive scenarios |

Example:

```java
Student s = new Student();
```

Strong reference.

```java
WeakReference<Student> ref = new WeakReference<>(s);
```

Weak reference.

If:

```java
s = null;
```

and no other strong reference exists, the `Student` object may be collected.

---

### 42. Weak Reference and GC — Important Interview Point

Consider:

```java
Student s = new Student();

WeakReference<Student> ref =
        new WeakReference<>(s);

s = null;
```

Now:

```
Strong references → none
Weak reference    → exists
```

The object is **eligible for GC**.

After GC:

```java
ref.get()
```

may return:

```
null
```

But don't say:

> "Calling GC immediately deletes the object."
> 

Correct statement:

> Once an object is no longer strongly reachable, it becomes eligible for GC. The JVM decides when and how it is actually reclaimed.
>

### 43. Strong vs Weak References — Complete Picture

```
                    Object
                 ↑
          ┌──────┴───────┐
          │              │
   Strong Reference   Weak Reference
          │              │
   Keeps object alive   Doesn't prevent GC
          │              │
          ↓              ↓
     GC cannot       Object may be
     reclaim it      reclaimed
```

For placement interviews, remember these five points:

1. **StackOverflowError** → thread stack exhaustion, commonly infinite/deep recursion.
2. **OutOfMemoryError** → JVM cannot satisfy a memory/resource allocation request.
3. **Memory leak** → unnecessary objects remain reachable, so GC cannot reclaim them.
4. **Strong reference** → normal reference; keeps object strongly reachable.
5. **Weak reference** → does not prevent GC from reclaiming the object.
